# COD money in the ledger, and automatic settlement statements (Work 97)

This Work closes Phase 1 audit gap G4: cash-on-delivery money never reached the ledger, so COD
sales were missing from settlement and reconciliation. It follows the owner's decision of
2026-11-07.

## 1. A pharmacy is owed COD money only once the cash reaches PharmaLink

| Moment | Ledger |
|---|---|
| The driver collects cash (`delivery.cod.collected`) | Nothing. The cash is not PharmaLink's yet. |
| The delivery channel hands the cash to PharmaLink (`delivery.cod.remitted`) | The COD sale is posted for the amount handed over. |

Posting `COD-<remittanceId>`, type `COD_SALE` (new enum value, additive migration
`20261108010000_module07_cod_sale_ledger_type`):

```
DEBIT  COD_CLEARING        handed over (at most the order total)
DEBIT  PROMOTION_EXPENSE   order.discountTotal   (platform-funded coupon, if any)
CREDIT PROVIDER_PAYABLE    handed over − commission + discount
CREDIT PLATFORM_REVENUE    order.platformFee     (PharmaLink's commission)
```

The split is a gateway capture's (`FeeCalculator.splitCapture`), with COD clearing in place of
gateway clearing.

- **Settlement.** It pays the posting like any other movement on the pharmacy's payable. Its
  "customer cash collected" now counts COD clearing as well as gateway clearing.
- **A short handover** pays the pharmacy only what reached PharmaLink. The difference stays with COD
  reconciliation and disputes.
- **An overage** is capped at the order total.
- **A handover smaller than the commission**, or one for an unknown order, posts nothing. It is
  logged for finance.
- **Idempotent.** A redelivered event finds the posting by its reference and posts nothing.
- `CodRemittedHandler` (Module 07) is the consumer that module-08 F-COD-01 names ("reconcile to
  Payment").

## 2. Statements generated by an amount, or by a period, whichever comes first

| Setting (Module 16 → Configuration, namespace `settlement`) | Environment default | Meaning |
|---|---|---|
| `autoRunMinAmount` | `SETTLEMENT_AUTO_RUN_MIN_AMOUNT=1000000` (10,000 ETB in santim) | Generate a statement once the pharmacy's unsettled payable reaches this. `0` turns it off. |
| `autoRunPeriodDays` | `SETTLEMENT_AUTO_RUN_PERIOD_DAYS=7` | Generate a statement once this many days have passed since the last one. For a first statement, the days count from the oldest unsettled posting. `0` turns it off. |

`SettlementAutoRunJob` runs hourly; like every job, it is off in tests and CLI processes. For each
pharmacy payable account, it derives the unsettled payable from the end of the last statement to
now. If either trigger is met, it runs the same `RunSettlementCommand` finance uses. That command
is audited, derives from the immutable ledger, and never counts a posting twice. The amount
trigger wins a tie.

**It only generates the DRAFT statement.** Approval and payout still need two finance officers
(maker-checker, NFR-SEC-06, Works 82–83). Nothing automatic moves money.

## Not covered

- **COD corrections after a remittance** (`delivery.cod.correction_recorded`) do not adjust the
  posting. A corrected handover amount is a finance adjustment.
- **Payouts still credit gateway clearing** (Work 83) whatever the money's channel. COD clearing's
  debit balance is the COD cash PharmaLink has received.
