# PharmaLink Ethiopia — Architecture Decision Log (ADRs)

Lightweight record of significant, hard-to-reverse decisions. Each entry: context, decision, consequences, status. New decisions append here; superseded ones are marked, not deleted.

**Status legend:** `Accepted` · `Proposed` · `Superseded` · `Deprecated`

---

## ADR-001 — Modular monolith (not microservices) at launch
**Status:** Accepted
**Context:** Small team, evolving domain, need velocity and transactional consistency across order/payment/inventory.
**Decision:** Build a single NestJS deployable, internally partitioned into 16 bounded-context modules with Clean Architecture. Communicate in-process via typed ports + a domain-event bus.
**Consequences:** Fast to build, one DB, strong consistency where needed. Requires discipline: no cross-module table reads, dependencies only via ports/events. Extraction to services later is enabled by ADR-002.

## ADR-002 — Cross-module references are scalar UUIDs, not Prisma relations
**Status:** Accepted
**Context:** We want bounded-context isolation and a clean future path to service extraction, without sacrificing intra-module referential integrity.
**Decision:** Foreign references *across* modules are plain `String` UUID columns with **no** Prisma relation. Relations are declared only **within** a module. Cross-context integrity is enforced in the application layer and via events.
**Consequences:** Each module's tables can be moved to a separate database with minimal schema change. Trade-off: no DB-level FK enforcement across contexts — covered by application invariants, events, and tests.

## ADR-003 — Prisma multi-file schema folder, one file per module
**Status:** Accepted
**Context:** A single monolithic `schema.prisma` would be unreadable at 16 modules and would blur ownership.
**Decision:** Use Prisma's schema-folder feature (`prisma/schema/NN-*.prisma`), one file per module + `00-config.prisma`.
**Consequences:** Clear ownership mirroring the architecture. Caveat: **Prisma merges all files into one global namespace**, so model/enum names must be globally unique (see ADR-008).

## ADR-004 — Pin Prisma 6; defer Prisma 7
**Status:** Accepted
**Context:** `prisma@latest` now resolves to 7.x, which removes `datasource.url` from the schema (requires `prisma.config.ts` + client adapters) — a breaking change with no functional benefit for us today. The schema-folder feature is GA in Prisma 6.
**Decision:** Pin `prisma` and `@prisma/client` to `^6.2.0`. Validate/format/migrate with Prisma 6.
**Consequences:** Stable, documented workflow (`DATABASE_URL` env + `datasource.url`). A future Prisma 7 upgrade is a tracked, isolated task: migrate datasource config to `prisma.config.ts` and adopt the client adapter. Not a launch blocker.

## ADR-005 — Money as integer minor units + currency string
**Status:** Accepted
**Context:** Floating-point money causes rounding errors; multi-currency (ETB primary) must be explicit.
**Decision:** All monetary values are `Int` minor units (e.g., santim) plus a `currency` string (default `ETB`). No floats for money, ever.
**Consequences:** Exact arithmetic. Formatting/localization handled at the edges. Ledger entries and balances all follow this.

## ADR-006 — Append-only ledgers as source of truth; balances derived
**Status:** Accepted
**Context:** Money, stock, dispensing, and driver earnings need auditability and reconstructable state.
**Decision:** Use append-only ledgers (`ledger_entries` double-entry for money, `stock_movements`, `dispense_records`, `driver_earnings`). Cached balances (`account_balances`, listing quantities) are derived and rebuildable from the ledger.
**Consequences:** Full auditability and safe recovery. Requires a balance-projection path and reconciliation tests. Never mutate a ledger row.

## ADR-007 — Reservation/hold + TTL for all scarce resources
**Status:** Accepted
**Context:** Stock and appointment/diagnostic slots are contended; overselling/double-booking is unacceptable.
**Decision:** Reserve via atomic conditional updates with a TTL hold; a sweeper releases expired holds. Applied to stock (04), appointment slots (10), and diagnostic capacity (11); consumed by the checkout/booking saga (06).
**Consequences:** Concurrency-safe allocation. Requires a sweeper worker and idempotent confirm/release. Holds are short-lived and observable.

## ADR-008 — Global name uniqueness; split notification preferences by concern
**Status:** Accepted
**Context:** ADR-003's merged namespace collided: Module 02 and Module 13 both defined `NotificationCategory` + `NotificationPreference`.
**Decision:** Keep both but disambiguate. Module 02 owns `NotificationCategory` + `notification_preferences` (user-facing category toggles). Module 13 owns `MessageCategory` + `channel_preferences` (`ChannelPreference`, delivery-engine per-channel routing + digest). Module 13 honors Module 02's toggles at send time.
**Consequences:** Both concerns modeled cleanly; no name clash. General rule: prefix/namespace module-specific enums and models to avoid future collisions.

## ADR-009 — Envelope encryption for health/PII artifacts; store references only
**Status:** Accepted
**Context:** Prescriptions, diagnostic results, and health records are sensitive and regulated.
**Decision:** Encrypt artifacts with envelope encryption (KMS-managed data keys). Persist only storage/key references (`*Ref`) in Postgres — never plaintext health data or card data, and never in logs.
**Consequences:** Strong data protection and key rotation. Requires a KMS integration and a crypto helper in `shared/`. Access is consent-gated and access-logged (Module 12).

## ADR-010 — Reliable eventing via outbox; in-process bus now
**Status:** Accepted
**Context:** Dual-writing to DB and a broker risks lost/duplicated events.
**Decision:** Producers write domain events to an `outbox` table in the same transaction as state changes; a relay worker publishes them. At launch the bus is in-process (typed) with a relay; the outbox makes a future broker (e.g., Kafka/RabbitMQ) a drop-in.
**Consequences:** No lost events, at-least-once delivery, idempotent consumers required. Contracts governed by `00-domain-event-catalog.md`.

## ADR-011 — Postgres FTS + geo at launch; OpenSearch behind a port
**Status:** Accepted
**Context:** Unified search (14) needs typo-tolerant, geo-aware ranking, but a separate search cluster is operational overhead early.
**Decision:** Launch on Postgres (`pg_trgm`/GIN + PostGIS or lat/lng) fed by CQRS projections. Abstract behind `ISearchEngine` so OpenSearch is a later, non-invasive swap.
**Consequences:** Lower ops cost at launch; clear scale path. Search owns no source data — it projects events from 03/04/09/10/15.

## ADR-012 — Hash-chained, append-only audit log
**Status:** Accepted
**Context:** Compliance and dispute resolution require tamper-evident records of privileged actions.
**Decision:** `audit_logs` (Module 01) is append-only; each entry stores `prevHash` + `entryHash` forming a verifiable chain. Admin (16) reads it but cannot mutate.
**Consequences:** Tamper-evidence and maker-checker support. Requires a verified write path and a chain-integrity test.

## ADR-013 — Serializable isolation + bounded retry required whenever a mutation co-locates its audit entry in the same transaction
**Status:** Accepted
**Context:** `AuditService.record(params, tx)` (`shared/audit/audit.service.ts`) reads the current chain tail (`findFirst orderBy createdAt desc`) and inserts a new entry bound to that `prevHash`. When a caller passes its own transaction (`tx`), `AuditService`'s own code comment already documents that "preserving the 'no fork' guarantee... becomes the CALLER's responsibility." Two concurrent `Read Committed` transactions can both read the same `prevHash` and both commit successfully (no unique constraint prevents it) — this silently **forks** the tamper-evident chain rather than raising a detectable conflict. Modules 02 (Profiles, retrofitted after `DEFECT-PROFILES-002`) and 03 (Catalog, built-in from day one) both independently converged on the same fix: run every mutation transaction that writes state + audit + outbox together at `Serializable` isolation, with a bounded retry (`TRANSACTION_RETRY_MAX_ATTEMPTS = 5`) on the resulting Postgres write-conflict codes (`P2034`/`40001`/`40P01`). This was never promoted to a formal, named decision, so Module 04 (Pharmacy & Inventory) independently chose `Read Committed` + `SELECT ... FOR UPDATE` for its own (correct, and separate) reason — quantity-correctness for stock reservations does not need `Serializable` — **without noticing that its own `audit.record(..., tx)` calls (present in at least 10 of its commands) inherit the fork risk this ADR describes**, since row-locking the `inventory_listings`/`stock_batches` rows does nothing to serialize concurrent inserts into the unrelated, unlocked `audit_logs` table.
**Decision:** Any module whose mutation commands write a state change, an audit entry, and an outbox event inside one transaction (the ADR-010 pattern, which is now the default for every module) **must** run that transaction at `Prisma.TransactionIsolationLevel.Serializable` and wrap it in a bounded-retry helper (mirroring `modules/catalog/application/support/dedup-conflict.ts`'s `runWithDedupRetry`/`isSerializationConflict`), unless the module can show its audit writes are *not* co-located in the same transaction as its row-locked mutations (in which case a narrower, documented exception is acceptable — see consequence below). Row-level locking (`FOR UPDATE`) remains the correct, separate mechanism for domain-quantity correctness (stock, ledgers) and is not a substitute for this rule.
**Consequences:** Modules 02 and 03 already comply. **Module 04 does not** — this is flagged here as a known, pre-existing gap in already-shipped, QA-verified code, out of scope for any single module's spec to silently fix; it is called out explicitly (`backend/docs/04-pharmacy-inventory-spec.md` should gain a defect note, and a dedicated hardening ticket should verify whether the gap is real under production concurrency or provably unreachable at Module 04's actual write volume) rather than left as an undocumented landmine. Every module built from this point forward (starting with Module 05) must apply this ADR from day one, the same way Module 03 did.

## ADR-014 — Cross-module port calls that each open their own transaction are an accepted eventual-consistency seam, not a distributed transaction
**Status:** Accepted
**Context:** ADR-001/ADR-002 keep modules DI-wired via ports rather than sharing a Prisma relation or a hand-rolled cross-module transaction. When Module X's command both (a) writes its own aggregate state in its own `IUnitOfWork` transaction and (b) calls into Module Y's exported port (e.g. `IInventoryPort.reserve()`), which opens *its own*, separate transaction, there is no way for X's transaction and Y's transaction to commit or roll back together without violating ADR-001/002's module-boundary discipline (Prisma cannot honor a single `$transaction` spanning two independently-owned unit-of-work implementations without collapsing the module boundary). The first concrete instance is Module 05's `SelectMatchCommand`, which updates its own `MatchRequest` row and separately calls Module 04's `IInventoryPort.reserve()`.
**Decision:** This is an **accepted, documented eventual-consistency seam**, not a defect to eliminate by inventing a distributed-transaction mechanism. Each such call site must: (1) call the downstream port *before* or *after* its own commit in a well-defined order (prefer calling the side effect with a self-healing compensating mechanism — e.g. a TTL — last, so a failure after it leaves the *cheaper-to-detect* side uncommitted); (2) document in its own module spec which side can be left orphaned and why that orphan self-heals (e.g. Module 04's reservation TTL sweeper reclaims an orphaned `HELD` reservation even if the caller's own bookkeeping update never lands); (3) not be silently assumed atomic. A true multi-step saga with explicit compensation (not just a hopeful TTL) is Module 06's `CheckoutSaga` pattern (`00-shared-conventions.md` §7) — reach for that, not a bespoke two-phase hack, once a call site's failure mode is not safely self-healing.
**Consequences:** Module specs must call out every cross-module port call that isn't wrapped by a saga and state the accepted orphan/compensation story explicitly (Module 05 §12 does this for `SelectMatchCommand`/`RematchCommand`). This does not block implementation — it is a documented risk acceptance, and it establishes the standing convention for Module 06 (checkout), Module 10 (booking), and Module 11 (diagnostics booking), all of which will hit the identical shape.

## ADR-015 — Product pricing is split: Catalog owns the platform reference price, Inventory owns the per-pharmacy selling price
**Status:** Accepted
**Context:** `architecture/module-03-catalog.md` §3.6 originally carried the boundary note "Catalog does **not** own price or stock," written when `products` had no price column and the only price in the system was `inventory_listings.price` (Module 04's per-pharmacy selling price). Module 06's checkout then specified order pricing as a fresh read of "real Module 03 prices" via `ICatalogPort.getProduct().price` (`backend/docs/06-orders-spec.md` §3.12 invariant 2, §5), because an order's total must be pharmacy-independent at the moment it is priced and must not be trusted from the cart's cached `CartItem.indicativePrice`. That contract was unimplementable against the schema as it stood, so a nullable `products.price` column was added (migration `20260906000000_catalog_product_price`) — leaving the Module 03 doc asserting the exact opposite of what the code now did. A second, subtler gap followed: the column existed but Module 03's own aggregate, repository, detail view and admin DTOs all dropped it, so the only way to set a catalog price was a raw Prisma write from outside the module — Catalog was the nominal owner with no ownership mechanism. Both halves are now fixed in code; this ADR records the boundary so the contradiction cannot silently return.
**Decision:** There are **two distinct prices with two distinct owners**, and they are never conflated. (1) **`Product.price`** (`products.price`, Module 03 — Catalog) is the **platform reference price**: pharmacy-independent, integer ETB minor units per `00-shared-conventions.md` §11 (never a float, never negative), and **nullable**, where `null` means *not priced, therefore not purchasable* — never "free". It is curated only through Catalog's own aggregate/repository and admin routes; no other module writes it. (2) **`InventoryListing.price`** (Module 04 — Pharmacy & Inventory) is the **per-pharmacy selling price**: what one branch charges for its own listing, pharmacy-set and audited there. Catalog has no authority over selling prices; Inventory never writes back to the reference price; Slice 1 imposes no ceiling or parity rule between the two. **Module 06 consumes, and never owns, pricing** — checkout takes the authoritative unit price from `ICatalogPort.getProduct().price` at placement time and snapshots it into `OrderLine.unitPrice`; `CartItem.indicativePrice` is a display cache and is never authoritative, so a catalog reprice between add-to-cart and checkout is charged at the current price. An unpriced product surfaces as a `null` port result and is rejected through the existing `CATALOG_PRODUCT_NOT_FOUND` path rather than priced at zero.
**Consequences:** Module 03's §3.6 boundary note is rewritten (Catalog owns the reference price, not selling price, not stock) and Module 04's boundary recap and open pricing question are updated to match. Browse/list/search projections stay **deliberately price-free** — the reference price is served only on the single-product detail read, so list rendering stays cacheable and Search remains the composer of selling-price/stock/distance ranking. Whether `InventoryListing.price` should be *constrained* by the reference price (a ceiling or parity rule for essential medicines) remains genuinely open and is explicitly **not** decided here — see `module-04-pharmacy-inventory.md` §16 question 4. Any future module that introduces a third price (promotions, insurance-negotiated rates) must state its owner against this ADR rather than overloading either existing field.

## ADR-016 — Partial-refund platform-fee clawback is proportional, cumulative, and rounded half-up, with the provider leg absorbing the balance
**Status:** Accepted
**Context:** `module-07-payment-wallet.md` §11.4 specifies only that a refund must "reverse provider-payable/revenue proportionally". Proportion on integers is not a complete instruction: it leaves the rounding direction, the precision, and — critically — the treatment of residues across a *sequence* of partial refunds undefined. Two defensible conventions differ by one santim per refund, and under per-refund independent rounding a payment refunded to 100% in several increments can leave `PLATFORM_REVENUE` permanently non-zero. That is a ledger that never reconciles, which BRULE-25 and §5.3 exist to prevent. The refund implementation (`e974512`) therefore refused a partial refund of a fee-bearing capture outright rather than pick a rule (`PaymentErrors.refundFeeAllocationUndefined`), deferring the decision to this ADR. The refusal is currently unreachable in practice because `orders.platformFeePercent` is undeclared in `env.validation.ts`, so every order carries `platformFee = 0`; it becomes reachable the moment a commission is configured.
**Decision:** For a refund of `r` against a payment whose capture posted gross `G` and platform fee `F`, where `P` is the total already refunded **and posted to the ledger** for that payment (the sum over `COMPLETED` refunds; `PENDING` and `FAILED` refunds have no posting and are excluded), the clawback is computed on the **cumulative** refunded amount, not on `r` in isolation:

```
feeClawbackCumulative(x) = round(F * x / G)        // half-up, whole minor units
feeClawback(this)        = feeClawbackCumulative(P + r) - feeClawbackCumulative(P)
providerClawback(this)   = r - feeClawback(this)   // the residual leg, by construction
```

posted as `DEBIT PROVIDER_PAYABLE providerClawback`, `DEBIT PLATFORM_REVENUE feeClawback`, `CREDIT <destination> r`, omitting any zero leg. Four properties follow, and each is traceable to an existing authority rather than chosen freely:

1. **Exact balance (§5.3, ADR-006).** The provider leg is *defined* as the residual, so the debits sum to `r` identically. No posting can fail to balance because of rounding.
2. **Half-up rounding to whole minor units (ADR-005).** This is not a new convention: `Fee.applyTo` already rounds half-up, mirroring Module 06's `PricingCalculator`, precisely so the fee a customer is quoted at checkout and the fee credited at capture cannot drift apart. A clawback that rounded differently from the capture it reverses would reintroduce exactly that drift.
3. **Zero residue on full refund.** When `P + r = G`, `feeClawbackCumulative(G) = round(F) = F`, so the fee clawbacks over any sequence of partial refunds telescope to exactly `F`. A payment refunded in full always returns `PLATFORM_REVENUE` to exactly zero, whatever the number, order or size of the increments. The final refund absorbs the accumulated residue automatically — no special case, and no "is this the last one?" test.
4. **Nothing new is stored (ADR-006).** `G` and `F` are read back off the committed `CAPTURE-<paymentId>` posting and `P` from the refunds already posted, so the rule is derived from the ledger. There is deliberately **no** residue column: a stored running remainder would be a second, mutable source of truth about money, which ADR-006 forbids.

The implementation must additionally assert `0 <= feeClawback <= r` and treat a violation as `LEDGER_UNBALANCED` — a defect tripwire in the module's established style, not a clamp.
**Consequences:** A given partial refund's split depends on its position in the sequence; that is the mechanism by which the residue self-cancels, and it is correct rather than an artifact. A refund posting therefore cannot be recomputed from a single refund row in isolation — it must be read from the ledger, which is already this module's rule for reconciliation. `PaymentErrors.refundFeeAllocationUndefined` and its refusal path **remain in force until this rule is implemented** in the follow-up code task; that task removes the refusal, implements the formula in `RefundAccountingService`, and adds the residue-telescoping regression tests. Two adjacent questions are explicitly **not** decided here and remain open product/compliance matters: (a) whether the platform should refund its commission on a partial refund *at all* — §11.4 says it does, and a decision to keep the commission (or to keep it only on customer-fault cancellations) would supersede this ADR; and (b) whether the delivery fee sits inside the refundable base, which is the second half of the module's own Open Question 3 and affects *what amount* is refunded rather than how it is split.

## ADR-017 — Refund eligibility is gated by payment state in Module 07 and by the triggering module's own policy; Module 07 owns no order-state whitelist
**Status:** Accepted
**Context:** BRULE-24 states that "refunds are issued only for eligible cancellations, failed deliveries, or verified disputes", and `module-07-payment-wallet.md` §3.2 F-RFD-03 calls for "refund eligibility checks tied to order state". Read literally that asks Module 07 to hold a whitelist of Module 06 order statuses. But every eligibility condition BRULE-24 names is owned elsewhere: an *eligible* cancellation is decided by BRULE-20 and Module 06's cancellation policy; a *failed delivery* is Module 08's `DeliveryStatus.FAILED` (module-08 §F-STS-01); a *verified dispute* is Module 16's `DisputeCase` reaching a refund `ResolutionAction` (module-16 §7, BRULE-50). Module 06's order-status table does not distinguish an eligible cancellation from an ineligible one, and Modules 08 and 16 are not built. Copying a status list into Module 07 would create a second cancellation policy free to drift from BRULE-20's — the failure mode ADR-002's ownership discipline exists to prevent.
**Decision:** Refund eligibility is enforced at **two separate gates, each owned by the module that can actually decide it.** (1) **Module 07's gate is payment state, and only payment state.** §6 already draws the authoritative line: a payment is refundable iff it is `CAPTURED` or `PARTIALLY_REFUNDED`, and an order cancelled *before* capture is compensated by `AUTHORIZED -> VOIDED`, not by a refund. Module 07 additionally enforces BRULE-24's arithmetic invariant (`refund <= captured - already refunded`) and §9.3's `finance:refund:any` + audit requirement for manual refunds. It holds **no** order-status list. (2) **The triggering module's gate is business eligibility.** Whether a given cancellation, failure or dispute *deserves* a refund is decided by the module that owns that fact, and reaches Module 07 as either a `SYSTEM` refund from that module's saga or a `MANUAL` refund carrying a named `finance:refund:any` actor recorded in `refunds.approvedBy`. The design's own control for the manual path (§3.2 F-RFD-03, §9.3 — permission plus audit) *is* the eligibility check for a human-judged case: a "verified dispute" is verified by a person, and this records which person.
**Consequences:** Exactly one refund path is reachable today — the **manual/admin** path, because no module yet calls Module 07's refund. Every automated trigger is **deferred with a named authoritative source**, and none requires a new Module 07 capability, since the command already accepts both `SYSTEM` and `MANUAL` initiators: order cancellation (`OrderCancelled` → 07 per `00-domain-event-catalog.md`; Module 06 integration task), Rx-rejection partial refunds (module-06 §4's "Rx rejected → refund Rx portion", which is fee-bearing and therefore *also* blocked on ADR-016), failed delivery (`DeliveryFailed` → 06 → 07, Module 08), dispute resolution (`DisputeResolved` → 06/07/08, Module 16 — this maps onto the manual path with an admin actor and needs no new mechanism), and appointment/diagnostic booking cancellations (`AppointmentCancelled`/`BookingCancelled` → 07, Modules 10/11). Note that BRULE-24's three named triggers are **not exhaustive**: the domain event catalog defines five distinct sources of a Module 07 refund, and two of them are not order-related at all — a further reason Module 07 must not gate on order state. Genuinely unresolved and **not** decided here: the content of BRULE-20's cancellation policy itself (cut-off, cancellation fee, partial charge) remains undefined in Module 06, and the module's own Open Question 6 (default refund destination — wallet versus original method, and any regulatory constraint) is still open.

## ADR-018 — `PARTIALLY_REFUNDED -> REFUNDED` is a required transition; §6's table omitted it
**Status:** Accepted
**Context:** `module-07-payment-wallet.md` §6 defines `CAPTURED -> REFUNDED` ("refund (full)") and `CAPTURED -> PARTIALLY_REFUNDED` ("refund (partial)"), and no transition out of `PARTIALLY_REFUNDED`. The refund implementation followed the table verbatim, so a sequence of partial refunds that exhausts the captured amount leaves the payment in `PARTIALLY_REFUNDED` even though nothing remains refundable; it records `paymentStatusAdvanced: false` in the audit trail rather than inventing the edge. The question this ADR settles is whether that omission was intentional.
**Decision:** It was **not** intentional; the edge is required, and §6 is corrected to include it. Three things in the design point the same way. First, §6 annotates `PARTIALLY_REFUNDED` with "remaining capturable tracked" — the state is defined by the existence of a remainder, so it cannot be the right state once the remainder is zero. Second, §5.3's invariant is written cumulatively (`refund <= captured - already-refunded`), so multi-refund sequences are explicitly in scope, and §11.4 selects the payment status as "REFUNDED/PARTIALLY_REFUNDED" without saying the choice is made once and never revisited. Third, and decisively: without the edge, two payments in *identical financial condition* — both refunded to 100% — hold different statuses depending only on whether the customer was repaid in one request or two. That makes `status` a record of request history rather than of the entity's state, which is the one thing a state machine must not be. The transition fires only when the refund that completes it leaves zero refundable; `REFUNDED` remains terminal.
**Consequences:** §6's table gains the row and §11.4 states the rule. The transition is **specified here but deliberately not yet implemented** — this was a decision task, and the code change belongs to a separate, focused follow-up: add the edge to `PaymentStatusPolicy`, let `RefundPaymentCommand.resolvePaymentTransition` advance the status (its "limitation" branch then becomes unreachable for this case), and update the two tests that currently assert and document the old behaviour. Until then the existing behaviour stands and remains money-safe: `refunds` and the ledger are authoritative for how much was refunded, and `remainingRefundable` already reports zero correctly. One adjacent gap is surfaced but **not** decided here: `PARTIALLY_REFUNDED` remains terminal with respect to `SETTLED`, so a partially-refunded payment can never enter a payout batch — which sits uneasily with BRULE-23's "provider payable = revenue - platform fee - refunds clawback", a formula that presumes partially-refunded orders *do* settle, net of the clawback. Whether §6 needs `PARTIALLY_REFUNDED -> SETTLED` is a settlement-module question and is left to that task.

## ADR-019 — A coupon discount is **funded by the platform**, booked as a `PROMOTION_EXPENSE` leg; the pharmacy is paid as if no coupon existed
**Status:** Accepted (mechanism, 2026-09-10) / **Resolved — platform-funded (2026-09-11)**
**Context:** Two independently-correct formulas meet for the first time when coupons are wired into checkout, and their combination decides real money that no document decides. Module 06's `PricingCalculator` computes `platformFee = round(subtotal * platformFeePercent)` from the **undiscounted** subtotal and then `grandTotal = max(0, subtotal + deliveryFee + platformFee - discountTotal)`. Module 07's capture (§11.3) posts `DEBIT GATEWAY_CLEARING gross`, `CREDIT PLATFORM_REVENUE fee`, `CREDIT PROVIDER_PAYABLE gross - fee`, where `gross` is `Order.grandTotal` and `fee` is `Order.platformFee` read back rather than re-derived (`FeeCalculator`). Substituting one into the other, a discount `D` yields `PLATFORM_REVENUE = platformFee` (unchanged) and `PROVIDER_PAYABLE = subtotal + deliveryFee - D`. **The pharmacy funds 100% of every coupon, and the platform's commission is charged on revenue the pharmacy never received.** No document states this. BRULE-23's "provider payable = order revenue - platform fee - refunds clawback" never defines whether "order revenue" is pre- or post-discount; module-06 §5.3's "totals = line prices + delivery + fees - discounts" defines only what the *customer* pays; module-07 §8 and F-STL-01 describe the fee leg and say nothing about promotions. The behaviour is an emergent consequence, not a decision — and it is currently **latent**: `orders.platformFeePercent` is undeclared in `env.validation.ts`, so every order carries `platformFee = 0`, and with a zero commission the pharmacy absorbs `D` while the platform earns nothing under any funding model. It becomes live and irreversible-in-effect the moment a commission rate is configured.
**Decision:** The *mechanism* is settled here; the *funding party* is not.

Accepted, and binding on the integration:

1. **One authoritative interpretation of order money.** `PricingCalculator` remains the sole owner of what the customer is charged. Module 07 never re-derives a platform fee — `FeeCalculator` reads `Order.platformFee`, for the reasons already recorded in its own doc comment — and never invents a second discount formula. `CouponValidator` answers exactly one question ("how much is this coupon worth on these lines") and never sees a platform fee.
2. **A coupon reaches the ledger only by reducing the captured gross.** There is no coupon-specific ledger leg today, and none may be added casually. The posting invariant is therefore unchanged by coupons and stated in full:

```
capturedGross = PROVIDER_PAYABLE credit + PLATFORM_REVENUE credit
capturedGross = subtotal + deliveryFee + platformFee - discountTotal
```

   No promotion leg appears because, under the current model, a discount is simply money never collected — there is nothing to post.
3. **`discountTotal <= subtotal` is load-bearing and must remain enforced.** `CouponValidator` already clamps a discount to the eligible subtotal, which is what guarantees `grandTotal >= platformFee` and therefore a non-negative `PROVIDER_PAYABLE`. Without that bound `Fee.applyTo` rejects a fee larger than the gross and the **capture** fails — days after checkout, with the customer's funds already authorized. Any future discount source (a second promotion, a wallet credit applied as a discount) must respect the same bound.

**Resolved (2026-09-11) — the platform absorbs `D`.** Product's decision is final: a coupon is a platform-funded promotion. Pharmacy proceeds are **not** reduced by it, and `Order.platformFee` keeps the Module 06 pricing contract unchanged. The three models that were on the table, and what was chosen:

| Model | Provider payable | Platform revenue | Verdict |
| --- | --- | --- | --- |
| Pharmacy-funded (the accidental pre-existing behaviour) | `subtotal + deliveryFee - D` | `platformFee`, on the pre-discount subtotal | **Rejected.** Charges the pharmacy for a promotion it did not run, and takes commission on revenue it never received. |
| **Platform-funded** | `subtotal + deliveryFee` (as if no coupon) | `platformFee`; net platform position `platformFee - D` | **Chosen.** |
| Split | `subtotal + deliveryFee - (1-share) x D` | as above, minus `share x D` | **Rejected.** Needs everything platform funding needs *plus* a per-coupon funding share and a rounding rule for splitting `D`. Not asked for. |

**The journal, and why a new account was unavoidable.** Paying the pharmacy as if no coupon existed means the capture's credits exceed the gross the customer actually paid, by exactly `D`:

```
DEBIT  GATEWAY_CLEARING   grandTotal                 what the customer actually paid
DEBIT  PROMOTION_EXPENSE  D                          the platform's promotional spend
CREDIT PROVIDER_PAYABLE   grandTotal - fee + D       = subtotal + deliveryFee
CREDIT PLATFORM_REVENUE   fee                        = Order.platformFee, unchanged
```

Both sides total `subtotal + deliveryFee + platformFee`. The promotion debit is therefore not bookkeeping colour — it is the only thing that makes the posting balance once the pharmacy is held whole, and the alternatives were to pay the pharmacy less (the rejected model) or to debit `PLATFORM_REVENUE`, which would merge commission earned with promotional spend and leave both unreportable. `LedgerAccountType` gains `PROMOTION_EXPENSE`, appended rather than inserted (an enum's declaration order is its sort order in PostgreSQL). It is platform-level, `owner_id = NULL`, and opened on first use by the existing `resolveAccount` path — no chart-of-accounts seed to extend.

**Refunds reverse it proportionally, from the ledger.** `RefundAccountingService` reads the promotion leg back off the committed `CAPTURE-<paymentId>` posting rather than re-deriving it from `Order.discountTotal`, exactly as it already does for the fee (ADR-016). The clawback gains a third cumulative term:

```
feeClawback       = round(F x (P + r) / G) - round(F x P / G)
promotionClawback = round(E x (P + r) / G) - round(E x P / G)      credited back to the expense
providerClawback  = r + promotionClawback - feeClawback            the balancing remainder
```

The roundings telescope as before, so any sequence of partial refunds summing to `G` returns all three capture legs to exactly zero. `E = 0` for every capture with no coupon, which collapses this to ADR-016's original two-term formula — so no historical refund behaviour changes.

**Consequences:** Un-discounted captures are untouched: a zero expense posts no leg, so the posting is byte-for-byte the three-leg transaction that existed before, and no empty `PROMOTION_EXPENSE` account is opened. `Order.platformFee` and `PricingCalculator` are unchanged — Module 07 still reads the fee rather than deriving it, and still owns no order pricing. The integration gate this ADR previously imposed is **lifted**: coupons may now be wired into checkout with a non-zero commission, because the funding model is decided and implemented. ADR-020 and ADR-021 still bind that work.

Two consequences reach beyond this task and are deliberately **not** implemented here. **Settlement** does not exist yet (no code, only a `SettlementStatus` enum and design text), so there is nothing to update; when it is built, BRULE-23's "provider payable = order revenue - platform fee - refunds clawback" must read the `PROVIDER_PAYABLE` balance, which already excludes promotional spend, and must not net `PROMOTION_EXPENSE` into either payable or revenue — the expense is the platform's own, and a payout batch that touched it would pay a pharmacy the platform's marketing budget. **Reporting** must likewise present `PLATFORM_REVENUE` and `PROMOTION_EXPENSE` as separate lines; the platform's net contribution on a discounted order is `fee - D`, which can legitimately be negative, and a report that showed only a netted figure would hide a promotion running at a loss. `discountTotal <= eligible subtotal` remains load-bearing for a different reason than before: it is what keeps `grandTotal >= platformFee`, and `Fee.applyTo` still rejects a fee larger than the gross.

## ADR-020 — A pharmacy-scoped coupon is evaluated after Module 05 matching; the pre-checkout preview is provisional by design
**Status:** Accepted
**Context:** `cart_items` carries no pharmacy. Module 05's matching chooses one during checkout, and `OrderLine.pharmacyId`/`Fulfillment.pharmacyId` exist only afterwards. §7's coupon `scope` nonetheless has a pharmacy dimension, so `POST /coupons/validate` can be asked a question a cart cannot answer; the implementation returns `PHARMACY_SCOPE_UNRESOLVABLE` rather than guessing. The question is whether that is a gap to close or the correct behaviour.
**Decision:** It is correct, and **the design already answers the timing question — no new mechanism is needed.** Module 06 §6's checkout saga orders the steps `1 validate cart -> 2 Rx gate -> 3 match (choose pharmacy) -> 4 reserve stock -> 5 compute totals (+ coupons/wallet, Module 07) -> 6 create Order -> 7 authorize -> 8 confirm`, and `backend/docs/06-orders-spec.md` §4 repeats that ordering for the implemented slice. **Matching (step 3) already precedes coupon evaluation (step 5).** Therefore:

1. The authoritative evaluation point is **checkout step 5, after matching**, where every scope dimension — product, category and pharmacy — is decidable from platform-determined data.
2. `POST /coupons/validate` is a **pre-checkout preview**, and is inherently unable to decide a pharmacy scope because no pharmacy has been chosen. `PHARMACY_SCOPE_UNRESOLVABLE` must remain a *distinct* reason rather than collapsing into "invalid", so a client can say "this offer applies at some pharmacies — continue to checkout" instead of telling the customer their code is bad.
3. **Rejected — a pharmacy on the cart.** It would create a second, client-influenceable pharmacy selection alongside Module 05's, which is precisely the authorization boundary the matching module exists to own. A coupon must never be the reason a customer can name their own dispensing pharmacy.
4. **Rejected — reordering the saga.** There is nothing to reorder: matching already comes first.

**Consequences:** The preview endpoint's answer for a pharmacy-scoped coupon is provisional, by design, and clients must treat step 5's figure as authoritative. A corollary worth stating: because matching is step 3 and totals are step 5, a pharmacy-scoped coupon can change the customer's total *after* the pharmacy is chosen — but the customer first sees the final figure at step 5, the same moment they see delivery and platform fees, so no additional confirmation step is implied. A client-supplied pharmacy "hint" remains forbidden even as an optimisation.

**One consequence surfaced after this ADR was accepted, and left for the integration task:** the exported contract cannot currently *ask* the step-5 question. `ValidateCouponInput` is `{ customerUserId, code, cartTotal? }`, and `ValidateCouponQuery` always scores the caller's active cart through `CouponLineResolver.forActiveCart`, which resolves every line with `pharmacyId: null`. So a step-5 caller — which has already matched a pharmacy and already re-priced its lines — would still receive `PHARMACY_SCOPE_UNRESOLVABLE` for exactly the coupon this ADR says is decidable there. Closing that is a contract change the Module 06 integration must make (quote against caller-supplied, already-matched lines), and it must stay **in-process**: extending `POST /coupons/validate` to accept a pharmacy would create the client-chosen dispensing pharmacy clause 3 forbids. Recorded in `module-07-payment-wallet.md` §11.7.1 and pinned by a test in `coupon.spec.ts`.

## ADR-021 — Exactly one coupon per order; stacking is not defined and must be refused
**Status:** Accepted
**Context:** §7's `coupon_redemptions` is unique on `(coupon_id, order_id)`, not on `order_id`, so the schema can store several different coupons against one order. Nothing in the design defines what that would mean. Both request shapes the design actually specifies are singular, however: module-06 §9's `POST /checkout` body carries `couponCode?`, and module-07 §9.5's validate takes `code`. The current implementation enforces only one redemption **per coupon** per order — a second, *different* coupon would be accepted by `ApplyCouponCommand` today.
**Decision:** **Exactly one coupon may be applied to an order.** The Module 06 integration must refuse a second coupon on an order that already holds an `APPLIED` redemption. Three reasons, in order of weight: both authoritative request shapes are singular, so stacking is not something the design asks for; no stacking rule exists anywhere to implement; and stacking would multiply the already-open funding question (ADR-019) by an ordering question, since with two coupons one must decide percentage-before-fixed versus fixed-before-percentage, whether the second coupon's eligible base is the already-discounted subtotal, and how each coupon's own `maxDiscount` interacts with the other's discount. Permitting stacking merely because the schema allows it would be inventing all of that.

Deliberately **not** defined here: the stacking order, the eligible base of a second coupon, and cap interaction. Those become questions only if product approves stacking, and that approval needs its own ADR.
**Consequences:** The rule is **not enforced in code today** — this was a decision task, and `ApplyCouponCommand` still rejects only a repeat of the *same* coupon. The integration task adds the check "no `APPLIED` redemption exists for this `orderId`", inside the same `Serializable` transaction as the redemption insert and for the same reason the usage limits are counted there: it is a cross-row condition, so no row-level constraint can express it. A `@@unique([orderId])` would be wrong, because a `REVERSED` row would then permanently block a legitimate re-application after a cancellation; the database-level form, if wanted later, is a partial unique index over `orderId WHERE status = 'APPLIED'`. Until the check exists, the only reachable path to a stacked order is an in-process caller, and there is none — `COUPON_PORT` has no consumer.

## ADR-022 — Payout execution needs its own `IPayoutProviderPort`; collection and disbursement are not the same operation
**Status:** Accepted
**Context:** Module 07 §11.5 names `IPayoutProviderPort.pay` but the repository has no such port, and the temptation when implementing F-STL-03 is to add a `pay()` method to the existing `IPaymentProviderPort` because both talk to "a provider". The two are different operations on different money. Every request type on `IPaymentProviderPort` is collection-shaped — `ProviderAuthorizationRequest`, `ProviderPaymentOperationRequest` and `ProviderRefundRequest` all carry `orderId`, `customerUserId` or `paymentId`, and `supports(method: PaymentMethod)` asks which customer instrument a gateway handles. A payout carries none of those: it addresses a settlement and a provider's beneficiary account. `IPaymentProviderRegistry` is collection-shaped too — `forMethod`/`forKey` resolve the gateway holding a *customer's* money, which is not how a disbursement rail is selected. In practice a payout is often a different product, a different credential set and a different contract at the same provider.
**Decision:** Payout execution goes behind a separate outbound port, `IPayoutProviderPort`, with its own registry, its own request/result types and its own normalized outcome (`PAID | ALREADY_PAID | PENDING | FAILED | UNKNOWN`, keeping `ALREADY_*` as the idempotent-retry answer and `UNKNOWN` never collapsible into `FAILED`). It must expose a status query as well as `pay` — an ambiguous payout with no way to ask the provider what happened has no resolution path, and the module already feels that gap where `ReconciliationService` reports every stuck payment as not automatically resolvable because no status adapter is bound. `IPaymentProviderPort` is not extended, and no existing adapter gains a payout method.
**Consequences:** A rail can serve collection, payout or both, by implementing one port or two. Existing adapters — including the fail-closed `TelebirrAdapter` — are untouched and do not acquire a method they cannot implement. Cost: a second registry and a second selection mechanism. The interface is deliberately **not written** until a named rail's contract exists (module-07 §15.12); a type contract with no rail behind it would fix decisions Open Question 4 has not made.

## ADR-023 — A payout in flight needs its own state; `APPROVED` and `FAILED` cannot represent an unconfirmed provider outcome
**Status:** Accepted
**Context:** `SettlementStatus` is `DRAFT | APPROVED | PAID | FAILED` and §11.5's flow is `DRAFT → approve → pay → PAID`. That leaves nowhere to put a payout that has been attempted but not confirmed — a timeout, a dropped connection, an unparseable response. The module has already settled the underlying principle for collection: `ProviderCaptureOutcome` and `ProviderRefundOutcome` both carry `UNKNOWN`, and both doc comments state that collapsing it into `FAILED` is the defect that produces a double movement. Payout is the same problem with the worst blast radius, because the money leaves the platform. With only the four existing states: leaving an in-flight payout `APPROVED` makes it indistinguishable from one nobody has attempted, so any retry sweep re-pays it; marking it `FAILED` frees it to be paid again.
**Decision:** The settlement lifecycle is `DRAFT → APPROVED → PROCESSING → PAID`, with `FAILED` reachable only from `PROCESSING` and meaning **the provider positively declined and no money moved**. An undeterminable outcome leaves the statement `PROCESSING` and writes nothing. `PROCESSING` is a new `SettlementStatus` value to be added by the implementing task. `FAILED → PROCESSING` is permitted for a deliberate retry, which always uses a new attempt identity (ADR-024).
**Consequences:** A statement always has an honest state, and "attempted" is never confused with "not attempted" or with "safe to retry". Requires a migration adding one enum value (appended, never reordered — the ADR-019 precedent), a reconciliation check for statements stuck in `PROCESSING`, and an operator path for resolving them. Open and deliberately undecided: whether a `DRAFT`/`APPROVED` statement can be withdrawn (a `CANCELLED` state) or must be superseded by an adjustment — a finance decision, recorded as Open Question 10 rather than guessed at here.

## ADR-024 — A payout carries two idempotency keys: one for the ledger posting, one for the provider call
**Status:** Accepted
**Context:** Every money operation in this module is made idempotent by a deterministic natural key with a unique index behind it — `ledger_transactions.reference`, `payments.idempotencyKey`, `coupon_redemptions (couponId, orderId)`, `settlements (pharmacyId, periodStart, periodEnd, currency)`. Payout appears to fit the same pattern with a single key on the settlement, but it does not, because it has two different exactly-once guarantees that a single key would conflate. If the provider call is keyed on the settlement, a legitimate retry after a *positive decline* is indistinguishable from a duplicate, and a provider idempotent on that key returns the original failure forever. This is precisely why `ProviderRefundRequest` is keyed on `refundId` rather than `paymentId`: one payment may have several distinct, legitimate refunds, and keying on the payment would make the second look like a retry of the first.
**Decision:** Two keys. The **ledger** posting is keyed `SETTLEMENT-<settlementId>`, enforced by the existing unique index on `ledger_transactions.reference` — one settlement is recorded as paid at most once, ever, whatever happens at the provider. The **provider call** is keyed `PAYOUT-<payoutAttemptId>` against a payout-attempt row committed to the database *before* the call is made, one row per attempt. A settlement may have several attempts; at most one of them moves money. An HTTP `Idempotency-Key` header is explicitly **not** the authoritative mechanism: it protects one client's retry and says nothing about a scheduler, a reconciliation sweep or a second operator.
**Consequences:** Retry-after-decline is safe and retry-after-ambiguity is representable. Requires a payout-attempt entity carrying the reference sent, the amount, the destination used, the normalized outcome and the provider's own reference — which is also the audit trail reconciliation needs (module-07 §15.10). The commit-before-call ordering is the same one `AuthorizePaymentCommand` already uses and for the same reason: it is the commit, not the constraint alone, that makes the *external* side effect idempotent.

## ADR-025 — Money moves only when a payout is confirmed; generating and approving a settlement post nothing
**Status:** Accepted
**Context:** §11.5 compresses generate, approve and pay into six lines, and it would be easy to debit `PROVIDER_PAYABLE` at approval — the amount is known and the decision is made. Doing so would record money as sent before anything sent it, in an append-only ledger where the entry can never be withdrawn, only offset. There is also a subtler trap: because balances are derived (ADR-006), "reserving" the payable with a mutable flag beside the derived balance would reintroduce exactly the authoritative-mutable-balance ADR-006 forbids.
**Decision:** The ledger changes at exactly one point. Generating a statement posts nothing (already true and asserted by tests). **Approving posts nothing** — approval is authorization to pay, not payment. Attempting a payout posts nothing. Only a **confirmed** payout writes `SETTLEMENT-<settlementId>`: `DEBIT PROVIDER_PAYABLE; CREDIT GATEWAY_CLEARING`, exactly once by unique index, after which the statement becomes `PAID` and `paidAt` is set. A positive decline posts nothing; an ambiguous outcome posts nothing. The payable is consumed by the debit itself — no freeze flag is added, because the debit already reduces the balance a later period derives. The amount disbursed is the statement's stored `netPayable`, never a fresh derivation: a re-derived figure could differ from the one an operator approved.
**Consequences:** The ledger never claims a payment nobody made, and a double-pay race is resolved by the database rather than by application locking. Note the figure asymmetry this makes explicit: `netPayable` is a *period* figure while the account balance is *cumulative*, and the two legitimately differ once a refund posts after the period closed — which is why payout debits the statement's amount and why late postings flow into the next period's statement rather than altering an approved one.

## ADR-026 — A payout destination is a separately modelled, verified beneficiary; Module 07 fails closed without one
**Status:** Accepted
**Context:** An inspection of the schema found **no payout destination anywhere in the repository**. `Pharmacy` carries a display name, ratings, transacting and licence status; `Organization` carries name, status, owner and licence. Neither has a bank account, account name, bank/branch identifier, Telebirr MSISDN or merchant id, or any verified beneficiary record; a schema-wide search for bank/IBAN/SWIFT/MSISDN fields returns only `PaymentMethod.BANK_TRANSFER`, which is a customer-side collection method. `ExecutePayout` therefore cannot be written at all today — there is nothing to address the transfer to. A misdirected transfer is also not recoverable by the platform, which makes this different in kind from a failed collection.
**Decision:** The destination is modelled as its own verified beneficiary entity, referenced from Module 07 by scalar UUID under ADR-002 — not as columns on `Pharmacy`, because a beneficiary has its own verification lifecycle, its own change history and its own access rules. Module 07 **fails closed**: a payout against a missing, unverified or since-changed destination is refused *before* any provider call, never attempted and reconciled afterwards. This is the same discipline `TelebirrAdapter` already applies to a missing integration contract — refuse precisely rather than guess. **No sensitive field is added by the task that records this decision.**
**Consequences:** Payout is blocked until the beneficiary contract exists, and that blockage is explicit rather than discovered during implementation. Left open deliberately, because each is a product/compliance answer rather than an engineering one: which module owns the beneficiary (Module 04's pharmacy profile, or Module 16, which already has the approval machinery and `ApprovalEntityType.PAYOUT`); the field set per rail, which cannot be fixed before Open Question 4 names the rails; who verifies a beneficiary and against what evidence; change control on a beneficiary, which is a high-value fraud target; and whether ADR-009's envelope encryption applies to account identifiers at rest. Recorded as Open Question 12.
